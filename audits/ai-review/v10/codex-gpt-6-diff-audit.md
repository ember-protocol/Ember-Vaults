The internal `admin::VERSION` changes from 5 to 6; it is a configuration gate, not the package's on-chain version number. The package identity evidence has a material inconsistency: current public [`deployment.json`](../../../deployment.json) still records the older v8 `0x4269cb19…809f` package, while public `Move.toml` names `0xb82df65c…b88e`. I could not query Sui mainnet from this environment, so I could not resolve the on-chain v10 object version, upgrade transaction, live vault fee settings, or source-to-chain equality. The Sui CLI is unavailable, so this was a static review: I read the relevant tests but did not execute Move tests, fuzzing, or a mainnet simulation. The separately archived October atomic-vault PDF was not used to establish finding dispositions; I could not extract and inspect its content here.

### E10-D01 — gross-priced EmberShare swaps can socialize source withdrawal fees

**Changed code.** The new [`do_swap_ember_shares_core`](../../../sources/atomic_liquidity_vault.move#L3749) values incoming source-vault receipt shares at the source's **gross**, floor-rounded collateral value ([`atomic_liquidity_vault.move:3831`](../../../sources/atomic_liquidity_vault.move#L3831)). It calculates the atomic swap fee and holdback from that gross value, pays the immediate amount from the atomic vault, and books its swap fee as an accrued platform-fee claim ([lines 3931–3984](../../../sources/atomic_liquidity_vault.move#L3931)). Later, [`redeem_collected_ember_shares`](../../../sources/atomic_liquidity_vault.move#L4376) submits those shares to the source vault's withdrawal queue with both `owner` and `receiver` set to the atomic vault's address ([lines 4403–4411](../../../sources/atomic_liquidity_vault.move#L4403)). The source [`process_request`](../../../sources/vault.move#L2301) deducts its permanent and any active time-based withdrawal fee unless that exact address is on the source's fee-exemption list ([lines 2335–2377](../../../sources/vault.move#L2335)). Neither the swap preview nor the swap core checks that fee or exemption.

**Scenario and impact.** With a zero atomic swap fee and holdback, source shares valued at 100 collateral units receive 100 units immediately. If the source deducts a 5% withdrawal fee when the atomic vault later redeems, it remits 95. The five-unit shortfall is borne by the atomic vault's backing and therefore its other share holders. A nonzero atomic swap fee need not cover this: it is accrued as a separate platform-fee claim, and [`collect_platform_fee(loss)`](../../../sources/atomic_liquidity_vault.move#L1877) can write off no more than the accrued amount. Swappers can repeatedly take this route subject to the configured capacity and utilization limits. The original user's holding period does not protect the atomic vault: its address normally has no source-vault deposit timestamp, so an enabled source time-based fee applies to its redemption.

**Preconditions and severity.** An atomic vault whitelists a source vault; users can swap that source's shares; the source charges a nonzero fee to the atomic vault address at *processing* time; and the atomic vault is not sufficiently buffered or repriced for that fee. The source operator may omit the exemption at setup or revoke it after a swap, and source fees can change while collected shares or queued redemptions remain in flight. The code comment at [`atomic_liquidity_vault.move:4369`](../../../sources/atomic_liquidity_vault.move#L4369) recognizes that the source operator **should** exempt the atomic vault; that operational step is not enforced. This is rated Low because it depends on the trusted source-vault configuration and is not known to occur live. I did not verify the live source-vault configurations or observe a loss transaction. The cross-vault scenario tests set source fees to zero ([`test_atomic_utilization_scenarios.move:65`](../../../tests/test_atomic_utilization_scenarios.move#L65)), so they do not cover this condition.

**Recommendation.** Prevent swaps from pricing source shares above reliably recoverable collateral. Expose and validate the effective source redemption fee and atomic-address exemption, then account for the fact that both can change before settlement: either guarantee the exemption for all outstanding atomic exposure at the source-vault level, or price/escrow against a bounded worst-case fee and cap the exposure accordingly. Add a fee-bearing source-vault test that swaps, queues redemption, processes it, and checks atomic-vault backing and fee liabilities; also test exemption revocation between swap and processing. Until the mechanism is enforced, verify exemption and fee settings for every whitelisted source and pause new swaps when they change.

| [`vault` per-operation pauses](../../../sources/vault.move#L2074) | The new deposit, withdrawal, and privileged-operation flags are dynamic fields; the old whole-vault pause remains effective through an OR check. Existing `get_vault_paused` and its legacy event do not expose the new flags, so integrations must use the new getters/event to report operation status accurately. |
| [`common` fee calculation](../../../sources/common.move#L1), [`math`](../../../sources/math.move#L1), and [`queue`](../../../sources/queue.move#L1) | I traced widened TVL/fee arithmetic and queue callers in both vaults; no separate confirmed loss path emerged from these helper changes. |
| Suilend strategy principal paths | Market ID, coin type, and reserve index are committed and checked before supply. Strategy exit rejects residual collateral across all coin types; auto-withdraw paths assert exact delivery. Integration against the live Suilend package remains outside this static review because the local interfaces are aborting stubs. |
| Suilend exit procedure | The admin must claim accrued rewards before exiting the strategy: [`drain_suilend_obligation`](../../../sources/strategy.move#L503) sends the emptied obligation capability to `@0x0` after checking collateral deposits, and unclaimed rewards would then be inaccessible. The code documents a same-transaction reward sweep through [`claim_suilend_strategy_reward`](../../../sources/atomic_liquidity_vault.move#L3170). This is an admin operational requirement, not classified as a vulnerability here. |
| Cross-vault operational documentation | [`ATOMIC_LIQUIDITY_VAULT.md`](../../../ATOMIC_LIQUIDITY_VAULT.md#L1164) still says source redemption records the *operator* as owner. The v10 code records the *atomic vault address*. Update the runbook so blacklist monitoring and source fee exemption target the correct address. |

This review does not establish the safety of older retained package versions, the live Suilend implementation, off-chain keepers, or the current mainnet configuration.
